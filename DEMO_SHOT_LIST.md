# Atlas demo — shot list

The three supplied recordings cover the product's working proof path. Keep the edits tight and show the on-chain boundary clearly; do not add new contracts or marketplace scope to this video.

## Source clips

| Order | File | Role in the story |
| --- | --- | --- |
| 01 | `CAMPAIGN STUDIO B2B.webm` | A protocol operator defines a campaign, its proof method, duration and reward budget. |
| 02 | `VERIFICATION ASSIGNATION GEMS.webm` | A participant completes the route, submits proof and sees the submission move through verification. |
| 03 | `approve gems.webm` | The operator reviews the shared queue, approves the proof and signs the Gem grant with the operator wallet. |

## Edit order

1. **Positioning (8–10s)** — Atlas landing or Learn hero. Establish: “Atlas is a SocialFi growth layer for Portaldot protocols.”
2. **Campaign Studio (20–30s)** — Use `CAMPAIGN STUDIO B2B.webm`. Keep the fields for campaign rules, proof method, cooldown and reward budget visible.
3. **Campaign Board (20–30s)** — Use the participant section from `VERIFICATION ASSIGNATION GEMS.webm`: choose the route, start it and submit the proof URL plus recipient wallet.
4. **Review and approval (25–35s)** — Use `approve gems.webm`: open the review queue, inspect the evidence, approve once and show the wallet signature. Avoid any duplicate approval click.
5. **Reward confirmation (15–20s)** — Return to the participant view from `VERIFICATION ASSIGNATION GEMS.webm`. Hold on the accepted state and the visible **ON-CHAIN REWARD / Gems confirmed** card, then open the explorer link if the recording includes it.
6. **Protocol value (10–15s)** — Close on Learn/architecture: campaign acquisition, participation, reviewable contribution and retention in one layer.

## Voiceover spine

> Atlas is a SocialFi growth layer for Portaldot protocols. Protocols create campaigns with clear rules. Communities complete quests and submit evidence. Operators review the contribution, and approved actions become visible progress and on-chain Gems. The result is a repeatable path from discovery to participation, verification and reward.

## Capture checklist before the final edit

- Use the latest production URL and the same two-browser setup used for the live queue.
- Show one participant proof and one approval only; do not re-submit an already approved proof.
- Keep the participant wallet and the operator wallet visually distinct.
- Capture the new Gem receipt card after approval so the reward is not represented only by a small toast.
- Record the voiceover separately; the final edit can be assembled after the audio arrives.
